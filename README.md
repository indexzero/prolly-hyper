# prolly-hyper

a port of mikeal/prolly-trees using hyperbee2 / hypercore

`prolly-hyper` is a port of [mikeal/prolly-trees](https://github.com/mikeal/prolly-trees) to the hyper stack. A prolly tree decides every chunk boundary from the hash of the entry at that position, so two peers that hold the same entries hold the same root. The port keeps upstream's read paths and `create`. It replaces upstream's incremental `bulk` with a canonical algorithm, so that every mutation lands on the root that `create` gives for the same entries. Node bytes use hyperschema-generated compact-encoding codecs. The address of a node is the BLAKE2b-256 hash of its bytes. Keys and values are bytes. The chunk factor and the collection kind, `map` or `set`, are consensus parameters: every peer must use the same ones, and the tree does not store them.

This stub is the state after dispatch D-003: the core tree, the map, the encoding, the chunker and the in-memory storage. Dispatch D-004 adds the set and `diff`. Dispatch D-005 adds the hyperbee2 storage and completes the docs: the API, the consensus parameters, the storage contract and the limits of the library.

`ProllySet` is a set of byte keys with no values, the port of upstream `cid-set.js`. A set leaf stores the key only, as its own node kind, so a set root differs from the root of a map with empty values. The chunk identity of a set entry is the hash of the encoded key, the same rule as the map. Upstream reads the cid bytes with no hash, so the port's set roots are not upstream's. `ProllySet.open(storage, { chunker, cache })` reads the root from storage. `add`, `delete` and `batch` each make one commit with compare-and-swap on the root they read. `has` and `keys({ gt, gte, lt, lte })` read. Duplicate keys in one batch collapse, and the last operation for a key wins. Two instances on one storage conflict: the second writer gets `CONFLICT`.

`diff(a, b, { stats })` takes two root nodes as `load` returns them, or `null` for an empty tree. The two trees may live in different storages. They must share the chunker and the collection kind, `map` or `set`, which the caller gives to `load`. A map root against a set root throws `KIND_MISMATCH`. The call is an async generator. It yields `{ key, left, right }` in key order for every key whose presence or value differs. A side is `null` when the key is absent there. For a map the sides are values. For a set they are the key. The merge is lazy and skips every shared subtree by address at the highest level where both cursors stand at its start, so a skipped subtree is never loaded. On two trees that differ in d entries it loads about O(d log n) nodes. `stats.visitedLeft` and `stats.visitedRight`, when `stats` is given, receive the hex addresses of the nodes it loaded.
